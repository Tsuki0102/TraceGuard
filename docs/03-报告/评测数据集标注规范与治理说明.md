### 1.1 与申报书"数据来源"承诺的差异说明（DOC-08）

申报书（创新训练计划项目申报表）表述数据集为"校企合作脱敏真实项目 + GitHub 开源项目构建"；

- **如实声明**：当前评测集为团队自建，**不含**校企脱敏项目与第三方开源项目；申报书表述为立项时的规划口径。
- **选择理由**：① 自建样例可精确控制 ground truth（缺陷位置/类型/一致性标注）与业务覆盖（电商订单/开放接口/在线考试），保证评测可复现性与标注权威性；② 符合 SRS 7.1"至少 3 个不同场景的真实 Java 项目"验收要求；③ 规避外部项目版权与数据脱敏合规风险。
- **扩充计划**：结项前按申报承诺**至少引入 1 个 GitHub 开源 Java 项目**（含需求文档的课设/管理系统）扩充评测集（增加需求条数与一致性标注对数），并同步更新本报告标注记录；当前逻辑还原 30 样本处于规范下限附近的局限已在《评测报告-逻辑还原》中如实注明。
- **结项口径**：若扩充未能完成，结项材料以本说明 + 各评测报告如实披露数据规模与构成，不虚报数据来源。

### 1.2 开源样例扩充方案（可选执行）

若需进一步扩大评测集规模与覆盖范围，按以下流程引入 GitHub 开源 Java 项目（当前 3 个自建样例已满足 SRS 7.1 验收下限，扩充为增强项）：

1. **选型标准**：含 README/需求描述的经典课设或管理系统（进销存/教务/图书管理/银行取款机等），代码 1000~3000 行、方法职责清晰、无外部框架强依赖（保证 Soot 编译路径可用）；优先 MIT/Apache 2.0 协议，记录授权与来源。
2. **注入**：代码复制至 `samples/<project>/code/`，编写 `requirements.txt`（按业务功能提取需求条目：编号/标题/描述/优先级）；人工注入代表性缺陷并记入 `defects.json`（缺陷须与需求语义可对照，注入口径同 GAP-035）。
3. **标注**：按本文件 3.1 一致性标注规则生成 `CL-xxx` 标注对，追加至 `samples/dataset/consistency-labels.json`（保持 `scope`/`requirementCode` 口径不变）。
4. **校验与评测**：`python scripts/validate-eval-dataset.py`（38 项检查）通过后，重跑 `DefectDetectionEvalTest` / `SpecConversionEvalTest` / `LogicDescriptionEvalTest` 并重新生成评测报告；同步更新本文件"数据集全景"表与《差距与改进编号台账》GAP-007/GAP-035 状态。
5. **披露**：扩充完成后在本节如实记录新增工程来源、协议、需求条数与标注对数；未扩充则按当前 3 样例规模如实披露。

## 2. 数据来源与构建方法

1. **样例工程**（GAP-035）：人工编写 3 个真实 Java 工程，每工程配 `requirements.txt`（需求条目）与 `defects.json`（注入缺陷权威清单）。
2. **一致性标注对**（GAP-007）：对"需求条目 × 代码方法"进行对齐（`requirementCode` 挂接），形成 65 个 `CL-xxx` 标注对；每对标注 `consistent`（一致）或 `defective`（存在缺陷，标注四类主类型之一，并通过 `defectId` 关联 Ground Truth 中的具体缺陷）。
3. **转换对照集**（GAP-007）：从三工程需求条目中选取 45 条（每工程 15 条均衡），人工编写 `referenceAlloy`（标准 Alloy 规约）与 `keyElements`（关键要素清单）。
4. **逻辑还原参考摘要**（GAP-006）：从通用 CRUD/聚合/分支/异常/资源/状态 6 类代码模式人工编写 30 个方法样例及中文参考摘要，覆盖简单到复杂逻辑。

## 3. 标注规则

### 3.1 一致性标注（CL 对）

- **`consistent`**：需求文本的约束、行为、状态流转在对应代码方法中得到满足；或代码仅为实现细节差异（命名/结构），不构成需求违背。
- **`defective`**：代码行为与需求明确要求相悖或缺失，且非命名/结构层面差异。须给四类主类型之一（见 3.2）。
- **排除规则（`scope=exclude`）**：仅含"基础代码缺陷"（空指针/空 catch/越界等，非需求违背类）的标注对不进入四类口径评测，避免与需求-代码一致性四指标混淆（CL-009/032/033/034/046）。
- **范围外对（`requirementCode` 为空）**：需求中不存在的代码方法（需求缺失）或代码中无需求依据的扩展实现（超范围实现），不进入一致性矩阵，由 `generateDefects` 未匹配检测产出（CL-061~065）。

### 3.2 缺陷四类口径（GAP-020）

| 主类型 | 定义 | 判定要点 |
|---|---|---|
| 需求缺失 | 需求明确要求的功能代码未实现 | 方法/字段/逻辑在需求中有、代码中无 |
| 代码超范围实现 | 代码实现了需求未要求的功能 | 以需求原文为准，禁止以"合理扩展"辩护 |
| 业务逻辑不一致 | 实现逻辑与需求行为相悖 | 条件反转、阈值不一致、计算错误、幂等窗口不符等 |
| 约束条件不满足 | 需求约束（数值/状态/格式/前置条件）未被代码校验 | 空值校验缺失、状态流转违规、长度/范围限制不符 |

> 判定优先级：与需求语义直接相悖 > 约束缺失 > 功能缺失 > 超范围实现。同一对仅标注一个主类型（`defectType`）。

### 3.3 转换对照集标注（SC 对）

- `referenceAlloy` 为人工编写的最低可校验规约（状态机/不变量/约束 fact），不追求工程级完整，追求**覆盖需求关键语义**。
- `keyElements` 抽取自需求原文，须含：结构要素（module/state/pred/fact/check）与业务关键词（金额、状态、约束值等）。
- 转换准确率口径（主）：生成规约校验非 failed 且 **语义要素覆盖率 ≥ 0.8**（GAP-052）；字面口径并列记录（GAP-013，warning 不阻断）。

### 3.4 逻辑还原参考摘要标注（M 样本）

- 摘要用中文描述方法**做什么、边界如何处理**（输入输出、异常分支、聚合逻辑），不描述实现细节（变量名、语句级）。
- 判分主口径（LLM judge）：参考摘要 vs 模型描述逐关键点核对，`score≥7` 且无幻觉判一致；降级口径（统计）：Embedding 余弦 ≥0.70 且内容词召回率 ≥0.55。

## 5. 数据结构 Schema

### 5.1 `consistency-labels.json`
```json
{
  "pairs": [{
    "id": "CL-001", "source": "ecommerce-order",
    "requirementCode": "REQ-001",
    "codeFile": "OrderValidator.java", "method": "validateAmount",
    "label": "defective", "defectType": "约束条件不满足",
    "defectId": "D05"            // 可选，仅 defective 且可定位到具体缺陷时
    , "scope": "exclude"          // 可选，仅 exclude
  }],
  "summary": { "total": 65, "inScope": 55, "consistent": 29, "defective": 26,
               "excluded_scope": 5, "out_of_scope": 5, "by_source": {} }
}
```
> 口径：`consistent/defective` 均指 **in-scope**（requirementCode 非空 且 非 exclude）对齐对；`excluded_scope` 与 `out_of_scope` 单列。不变量 `total = consistent + defective + excluded_scope + out_of_scope`。

```json
{ "defects": [{ "id": "D01", "project": "ecommerce-order", "file": "OrderService.java",
                "method": "loadDiscountConfig", "type": "约束条件不满足",
                "subType": "资源未释放", "relatedReq": "REQ-003" }] }
```

### 5.3 `spec-conversion-pairs.json`
```json
{ "pairs": [{ "id": "SC-EC-001", "source": "ecommerce-order",
              "requirementText": "REQ-001: ...", "referenceAlloy": "sig Order {...}",
              "keyElements": ["module", "amount", "> 0", ...] }] }
```

### 5.4 `detection-results.json`
```json
{ "results": [{ "id": "CL-001", "detected": false },
               { "id": "CL-003", "detected": true, "detectedType": "业务逻辑不一致" }] }
```

### 5.5 `samples/logic-eval/samples.json`

```json
   "reference": "创建用户：校验用户名非空，密码不为空则加密存储，..." }]
```

## 6. 质量与独立性控制

1. **来源可查**：所有标注对/缺陷均回溯到样例工程 `requirements.txt` 与代码文件，`defectId` 指向 Ground Truth 权威清单。
2. **工具化校验**：`scripts/validate-eval-dataset.py` 对 5 个数据集执行 38 项一致性/完整性/引用/统计校验（见第 8 节），任何增删改后必须全绿。
3. **防数据泄漏**：评测为"规则模板/真实算法链路"确定性执行 + LLM 仅做判定，数据集不参与模型训练，无训练集泄漏风险；标注对的 `codeFile/method` 指向样例工程，供外部复核者直接重查。
4. **交叉验证**：AUD-02 用独立 LLM 语义判定对人工标注进行二次复核（修正 9 对）；修正全部留痕可追溯。
5. **样本规模达标**：一致性 in-scope M=55（目标 40~100）、转换对 N=45（目标 40~60）、逻辑还原 30 样本，均落在达标区间，且三工程均衡。
6. **修复记录（2026-08-24 治理）**：
   - `consistency-labels.json` summary 口径统一（consistent=29/defective=26 均为 in-scope；新增 `out_of_scope=5`），消除 34+26≠65 的计数歧义；
   - `defect-ground-truth.json` `by_type` 与 defects 数组真实分布对齐（需求缺失 4 / 超范围 3 / 业务不一致 7 / 约束不满足 8 / 基础缺陷 12）；
   - 上述修复不影响任何 `pairs/defects` 业务字段，评测结果不变。

## 7. 可复现评测命令

> 前置：JDK 21+、Maven 3.8+；根目录 `.env` 提供 `QWEN_API_KEY` 等（可选，仅 LLM 判定路径需要）。

```bash
# 0) 数据集一致性校验（任何增删改后必跑，全部 PASS 方可发布评测数据）
python scripts/validate-eval-dataset.py

# 1) 规约转换评测（规则基线，确定性，不依赖 LLM）
cd backend && mvn -B test -Dtest=SpecConversionEvalTest

# 2) 规约转换评测（LLM 各模型路径，可选；GLM/DeepSeek/qwen 按 .env 配置）
mvn -B test -Dtest=SpecConversionLlmEvalTest

# 3) 缺陷检测四指标评测（LLM 语义判定）
#    a. 离线逐条产出 LLM 判定（推荐，规避 DashScope 连续调用节流）：
#       将每条标注对的 (需求原文, 代码内容) 调大模型判定，结果写入 backend/llm-verdicts.json，
#       格式 {"CL-001": {"consistent": true, "defectType": "", "reason": "..."}}
#    b. FUN-04b 双判定管线在线导出（本地 Ollama qwen2.5-coder:14b，主口径产出口径；
#       verdict 文件缺失时生效，双提示词交叉+规则仲裁+数值归属过滤后写 backend/llm-verdicts.json）：
mvn -B test -Dtest=DefectDetectionEvalTest \
    -Dllm.provider=codellama \
    -Dllm.codellama.baseUrl=http://localhost:11434/v1 \
    -Dllm.codellama.model=qwen2.5-coder:14b \
    -Dgap007.llm.export=llm-verdicts.json
#    c. 直接复算指标（读已有 llm-verdicts.json，离线确定性，不再调 LLM）：
mvn -B test -Dtest=DefectDetectionEvalTest
#    d. 未配置 LLM 且无 verdict 文件时自动 engine=rule（规则基线），报告如实标注。

# 4) 逻辑还原一致性评测（LLM judge 主口径；judge 不可用时统计降级口径）
mvn -B test -Dtest=LogicDescriptionEvalTest

# 5) 阈值标定（与缺陷检测同链路联动）
mvn -B test -Dtest=ThresholdCalibrationEvalTest

# 6) 评测报告自动汇总
#    SpecConversionEvalTest / DefectDetectionEvalTest 写入 docs/03-报告/评测报告-综合.md；
#    LogicDescriptionEvalTest 写入 docs/03-报告/评测报告-逻辑还原.md。
```

**结果稳定性声明**：
- 规则模式评测（规约转换规则基线 / 缺陷检测 engine=rule）为**确定性**执行——相同数据集 + 相同代码版本 → 相同指标，可直接复现。
- LLM 判定路径受模型/温度影响，为给出可复现基线，要求将每次评测的 LLM 判定结果保存为 `backend/llm-verdicts.json`（`DefectDetectionEvalTest` 优先读取该文件，存在则不再调 LLM）；历史报告中的 92.7%（LLM 55/55 成功）即基于该离线判定基线得出。
  **2026-08-27 起（FUN-04b）**：`DefectDetectionEvalTest` 新增导出模式——verdict 文件缺失且指定 `-Dgap007.llm.export=llm-verdicts.json` 时，由生产 `ConsistencyJudge.judgeDual` 双判定管线在线逐对判定并落盘（当轮同时用于指标计算）；当前 `backend/llm-verdicts.json` 即为该管线的最新产物，复跑评测只需 `mvn test -Dtest=DefectDetectionEvalTest` 即可离线复算出相同指标。

## 8. 数据集治理校验（工具化）

`scripts/validate-eval-dataset.py`（Python 3，仅标准库）对 5 个数据集执行 38 项检查：

| 维度 | 检查项举例 |
|---|---|
| 结构合法 | JSON 可解析、pairs/results/defects 非空、detected 为布尔 |
| ID 唯一 | CL/SC/缺陷/逻辑样本 ID 无重复 |
| 枚举合法 | label∈{consistent,defective}、defectType∈四类口径、source∈三工程、category∈六类 |
| 引用完整 | defectId 存在于 Ground Truth 且工程一致；codeFile/method 文件存在于样例工程 |
| 规模达标 | in-scope M=55≥40、转换 N=45∈[40,60]、逻辑样本 30 |
| 统计自洽 | 各文件 summary 与真实计数一致；不变量 total=consistent+defective+excluded+out_of_scope |

运行方式：`python scripts/validate-eval-dataset.py`，退出码 0 = 全部通过，1 = 存在失败项。
