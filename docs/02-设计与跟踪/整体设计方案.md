# TraceGuard 整体设计方案（概要设计）

> 对应 SRS 7.3 成果验收「整体设计方案」要求。本文档描述系统总体架构、模块划分、核心流程、数据模型与部署形态，与 `backend/`、`frontend/` 实际代码结构保持一致。
> 版本：TraceGuard V1.2；生成时间：2026-08-23。

---

## 1. 系统概述

TraceGuard 是面向「软件需求—代码一致性验证与缺陷自动检测」的 Web 系统，融合形式化需求规约（Alloy/Kripke）与大模型语义理解，覆盖五大能力：

1. 自然语言需求自动化形式化建模
2. Java 代码静态解析与语义提取（AST/CFG）
3. 需求—代码多维度一致性校验
4. 缺陷自动定位、分级分类与追溯
5. 可视化全流程管理（项目/任务/报表/配置）

目标用户：企业软件研发团队（项目经理、开发、测试）、高校师生（教学实训/科研验证）。

---

## 2. 总体架构

系统采用前后端分离的分层架构，满足 SRS 2.4「技术栈约束（纯 Java 技术栈 + Vue3，禁止 Linux 专属依赖，Windows 原生适配）」。

```
┌──────────────────────────────────────────────────────────┐
│ 前端（Vue3 + Element Plus + ECharts）                       │
│ Layout 布局 / 项目/任务/需求/代码/缺陷/追溯/报表/系统设置     │
└───────────────────────┬──────────────────────────────────┘
                        │ RESTful JSON（JWT 鉴权 + WebSocket 进度推送）
┌───────────────────────┴──────────────────────────────────┐
│ 后端（Spring Boot 2.7 + JDK 21）                            │
│  ├ Controller 层   （REST 接口、参数校验、鉴权拦截）          │
│  ├ Service 层     （业务编排：解析/形式化/一致性/缺陷/报表）   │
│  ├ Core 层        （ConsistencyChecker 三维相似度校验核心）   │
│  ├ LLM 层         （多引擎抽象：qwen/CodeLlama/Ollama，可切可回退）│
│  ├ Integration 层 （Jira/Zentao 真实 REST 对接）             │
│  ├ SPI 层         （多语言/多形式化语言扩展点）               │
│  ├ Task 层        （异步分析任务调度、暂停/恢复/终止控制）     │
│  ├ Util 层        （文档解析/代码解析/形式化生成/缺陷检测）   │
│  └ Mapper 层      （MyBatis-Plus 持久化）                    │
└───────────────────────┬──────────────────────────────────┘
                        │ JDBC
┌───────────────────────┴──────────────────────────────────┐
│ MySQL 8.0（业务数据） + 本地文件系统（需求/代码工程/备份）     │
└──────────────────────────────────────────────────────────┘
```

**设计原则**：高内聚低耦合、分层清晰、核心参数可视化配置（权重 α/β/γ、阈值 T1/T2、解析规则、LLM 参数）、预留多语言/多形式化扩展 SPI，满足 SRS 5.6 可维护性与可扩展性。

| 模块 | 对应 SRS | 核心职责 | 关键类 |
|---|---|---|---|
| 需求解析与形式化 | FR-REQ-001~004 | 文档解析（Word/PDF/MD/TXT）、歧义检测、Kripke 五元组提取、Alloy 规约生成与校验、优化建议 | `DocumentParserUtil`、`RequirementAnalyzerUtil`、`AlloyAnalyzerUtil`、`AlloySpecVerifierUtil`、`spi.AlloySpecGeneratorAdapter` |

## 4. 核心流程

### 4.1 分析任务主流程（AnalysisService）
```
上传需求文档 + Java 工程
  → 文档解析（分句 + 歧义检测 + Kripke/Alloy 形式化）
  → 代码解析（AST/CFG + CodeUnit 拆分 + 逻辑还原；
      二次分析按文件内容哈希做增量解析：未变更文件复用，仅重解析变更/新增文件）
  → 三维相似度一致性校验（ConsistencyChecker 门面）
  → LLM 语义二审（ConsistencyJudge，纠正规则漏检）
  → 缺陷生成与定位（含代码行号 Defect.defectLine、规则信号分解 Defect.riskSignals）
  → 双向追溯矩阵 + 统计 + 报告生成
  → WebSocket 实时推送进度，支持暂停/恢复/终止（协作式控制检查点）
```

### 4.2 缺陷精准定位
`DefectLocator` 按 `DefectSubType` 枚举绑定的 `LocatorStrategy` 用 JavaParser 定位语法节点：约束/校验缺失→方法体首条语句（校验插入位）、数值/阈值→与需求数值冲突的比较字面量行、状态→状态字段赋值行；AST 失败降级关键词启发式/方法首行，叠加 `CodeUnit.startLine`（锚定方法声明行、修正前导 javadoc 偏移）得源文件绝对行号，前端 `Defects.vue` 红色高亮命中行。

### 4.3 强制改密闭环（4.6 整改）
新建/重置密码置 `mustChangePassword=true` → `LoginInterceptor` 拦截该标志 → 前端登录后跳 `/change-password?forced=true`，未改密禁止进入业务页。

## 5. 数据模型（核心实体）

| 实体 | 说明 |
|---|---|
| `User` | 用户（角色/密码过期/强制改密标志/审计字段） |
| `Project` | 项目（需求路径/代码路径/解析范围/归档状态） |
| `AnalysisTask` | 分析任务（状态机/进度/权重阈值/控制标记） |
| `Requirement` | 需求（原文/Kripke/Alloy 规约/歧义标记） |
| `CodeUnit` | 代码单元（类/方法/字段，含 startLine/endLine/内容哈希 contentHash，增量解析用） |
| `ConsistencyResult` | 一致性结果（三维得分/总分/分级状态） |
| `Defect` | 缺陷（类型/子类型/等级/原因/修复建议/**defectLine 行号**/**riskSignals 规则信号分解**/代码与需求片段） |
| `CodeDefect` | 代码基础缺陷（Soot 静态检测） |
| `FormalSpecification` | 形式化规约（Alloy 文本/校验结论） |
| `AuditLog` / `DataChangeLog` | 操作日志（哈希链防篡改）/ 字段级变更 diff |
| `LlmConfig` / `LlmCallLog` | LLM 配置（provider/apiKey 加密存储）/ LLM 调用留痕 |
| `SystemConfig` / `BackupConfig` | 系统配置键值（热更新，含规则信号权重 `risk_weights`）/ 自动备份频率配置 |
| `ReportTemplateConfig` / `UserPreference` | 报告模板（创建者隔离、全局默认）/ 用户界面偏好 |
| `BaseEntity` | 公共审计字段基类（创建/更新时间、逻辑删除） |

## 6. 接口设计

- **用户接口**：左侧导航 + 右侧内容，核心操作 ≤3 次点击，错误提示含原因/方案，缺陷分栏对比 + 行号高亮（SRS 4.1）。
- **软件接口**：POI/PDFBox（文档）、JavaParser/Soot（代码）、Alloy Analyzer（形式化）、LLM API/CodeLlama（语义）、MySQL 8.0（持久化）、Jira/禅道（项目管理对接）（SRS 4.2）。
- **硬件接口**：纯软件架构，无需专用硬件；支持本地打印机直接打印报告、本地/外接存储导出（SRS 4.3）。
- **RESTful**：Swagger 文档化；JWT 鉴权；标准 CRUD + 批量导入导出 + 备份恢复接口。

## 7. 非功能设计

- **性能**：万行级 Java 全流程分析 ≤10 分钟（实测性能基准见 `性能基准报告-*`）；并发 3 任务并行（信号量限流，见 `ConcurrencyTest`）；响应 ≤2s、查询 ≤3s。
- **准确率**：逻辑还原一致率 **96.7%**（LLM judge 口径，30 样本 29 达标，《评测报告-逻辑还原》2026-08-25）；缺陷检测 **FUN-04b 双判定管线（本地 qwen2.5-coder:14b）实测（最新主口径）**——准确率 **96.4% 达标**（≥80%）、漏检率 **3.8% 达标**（≤15%）、误报率 **3.4% 达标**（≤10%，2026-08-27，LLM 55/55 成功；TP=25/FP=1/FN=1/TN=28，残余个案 CL-038 整除精度语义与 CL-047 简化占位实现标注争议，已在报告如实列示）；并列历史基线：单提示词 LLM 81.8%/7.7%/27.6%（2026-08-26）、qwen-max 83.6%/15.4%/17.2%（2026-08-25）、本地 CodeLlama 61.8%/0%/72.4%（2026-08-24）、规则 47.3%/0%/100%，规则链路经 FUN-04 二期增强后 BGE 标定链路最优 t1=0.46 下 61.8%/50.0%/27.6%，**P1-4 去噪+温和升权后 65.5%/46.2%/24.1%（2026-09-02 定稿，历史最高，见《阈值标定报告》与《评测报告-综合》缺陷检测章节，以报告为准）**。
- **安全**：两级权限 + 密码复杂度/过期 + 登录防爆破 + 上传加密存储 + 审计哈希链。
- **部署**：Windows 一键部署（`scripts/deploy-windows.ps1`）+ docker-compose；**JDK 21+**（SRS 2.3.2 基线文档写"JDK 1.8 及以上"为申报期口径，实际构建要求 JDK 21、Alloy 6.2.0 需 17+，以 README/部署手册为准）、**Node.js 20 LTS**、MySQL 8.0、主流浏览器（Chrome/Edge/Firefox 100+）。
- **可维护/扩展**：分层架构、可视化配置、SPI 多语言/多形式化扩展、独立测试接口。

---

## 8. 部署与扩展性

- **部署形态**：Windows 本地一键部署 / Docker 容器；数据全部本地处理，不上传第三方公有云（SRS 2.4 合规性约束）。
- **扩展性**：`spi` 包预留多开发语言（C#/Python）、多形式化语言（TLA+）扩展点；LLM 层多引擎抽象支持热切换与降级回退。
