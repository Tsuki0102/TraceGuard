# TraceGuard 用户操作手册

**版本**：V1.0（2026-08）
**适用对象**：平台普通用户、系统管理员
**系统名称**：TraceGuard 需求-代码追溯平台

---

## 1. 系统简介

TraceGuard 是一款基于形式化验证的**需求-代码一致性分析平台**，核心能力包括：

- 需求文档解析（Word / PDF / Markdown / TXT）与需求条目自动抽取
- 需求形式化规约生成与 Alloy 规约校验
- Java 代码工程解析（方法级单元、控制流图、语义向量）
- 需求-代码一致性检查（正向矩阵）与反向追溯矩阵（含中英文混合需求匹配）
- 缺陷管理（一致性缺陷 + 代码静态缺陷，支持需求/代码分栏对比与行号定位）
- 分析报表导出（Excel / Word / PDF）、数据加密备份与恢复、操作审计

## 3. 登录与注册

1. 打开系统地址，进入登录页。
2. **登录**：输入用户名、密码。同一账号**连续失败 5 次将被临时锁定 10 分钟**，锁定期间无法登录，请稍后再试。
3. **注册**：点击「注册账号」，填写用户名、姓名、密码。
   - 密码复杂度要求：**至少 8 位，且同时包含大写字母、小写字母和数字**。
   - 注册成功后系统置「**强制改密**」标志，**首次登录必须修改密码**方可进入业务页面（GAP-027 闭环）。
4. **强制改密（GAP-027）**：以下情形登录后会被拦截至「修改密码」页（路由 `/change-password`），完成修改前无法进入任何业务页面：
   - 新注册账号首次登录；
   - 管理员在「用户管理」中**重置密码**后（该用户「强制改密」状态标记为「待改密」）。
   - 修改成功后标志自动清除，下次正常登录。
5. 忘记密码：联系管理员在「用户管理」中重置。
6. **密码定期提醒（AUD-03）**：系统建议每 **90 天** 修改一次密码。当密码剩余有效期不足 **15 天** 时：
   - 登录成功后会弹出「密码即将过期」提示；
   - 进入「个人中心」会看到橙色「即将过期」标签与具体剩余天数，请尽快修改密码。
   - 注册与每次修改密码都会重置该倒计时。
7. **角色与数据权限（细粒度数据隔离）**：
   - 系统角色分为**管理员**与**普通用户**。管理类功能（用户管理、审计日志、系统设置、数据备份、密钥轮换、大模型/集成配置、入站同步）仅管理员可见可用；
   - **普通用户仅可见自己创建的项目**及其全部数据（需求、代码、缺陷、结果、导出、统计、追溯等），无法访问他人项目；
   - **报告模板按创建者隔离**：普通用户仅可使用系统内置模板与本人创建的模板，不能查看/编辑/删除他人模板；导出报告时若全局默认模板为他人私有模板，系统自动回退到内置「完整报告」模板，不会泄露模板内容。

## 6. 数据上传（项目详情页）

进入项目详情页后分两步上传。上传的需求文档与代码压缩包在服务器端以 **AES-256 加密存储**（明文不落盘），分析时自动解密读取，保障数据安全。

### 6.1 上传需求文档

- 支持 **Word (.docx)、PDF、Markdown (.md)、TXT**，可一次选择多个文件批量上传。
- 文档要求包含可识别的需求编号（如 `REQ-001`、`1.`、`FR-XX-001` 等常见编号格式），解析效果最佳。
- **重新上传会自动失效旧的需求解析结果与形式化规约**，下次分析重新生成。

### 6.2 上传代码工程

- **ZIP 压缩包**：zip 内应包含 Java 源码目录，系统自动解压并解析其中的 Java 方法单元。
- **单个/批量 Java 源文件**（4.4 整改项）：支持直接选择 `.java` 文件导入，**最多 50 个**批量上传，无需打包。
- 代码解析的**范围可在「系统配置 → 代码解析范围」中按包/类/方法过滤**（include 命中才解析，exclude 命中即排除，支持 `com.example.*`、`*service*` 等通配；保存后热生效）。
- **重新上传会自动失效代码解析结果及全部下游结果**（一致性、缺陷等）。

### 6.3 大文件分片上传（断点续传）

- 单文件**超过 10MB 自动切换分片模式**：按 5MB/片切片上传，页面显示实时进度条。
- 分片失败自动重试（最多 3 次）；网络中断后重新上传时，**已传分片自动跳过**，无需从零开始。

## 7. 分析配置与执行

项目详情页下方「分析配置」：

### 7.1 参数说明

| 参数 | 含义 | 默认值 | 约束 |
|---|---|---|---|
| 权重 α（语义） | 语义向量相似度权重 | 0.40 | α+β+γ = 1 |
| 权重 β（约束匹配度） | 代码对需求约束条件的满足程度权重 | 0.35 | 同上 |
| 权重 γ（不变量满足度） | 代码对形式化模型不变量的符合程度权重 | 0.25 | 同上 |
| 阈值 T1 | 一致性判定上阈值，Sim > T1 判为「完全一致」 | 0.80 | T1 > T2 |
| 阈值 T2 | 一般不一致判定下阈值，[T2, T1] 判为「一般不一致」 | 0.50 | 同上 |

三项权重之和必须等于 1，且 T1 必须大于 T2，否则无法启动。

> 阈值口径（对齐 SRS FR-CHECK-002）：`Sim > T1` 完全一致；`T2 ≤ Sim ≤ T1` 一般不一致；`Sim < T2` 严重不一致。
> 标定说明：《阈值标定报告》（2026-09-02 批次，P1-4 规则链路去噪+温和升权后）在标定链路参数（α/β/γ=0.2/0.55/0.25）下的推荐阈值为 **t1=0.46 / t2=0.33**（本数据集规则链路缺陷检测准确率最优，**65.5%**/漏检 46.2%/误报 24.1%；历史批次 61.8%/50.0%/27.6% 并列留档）；
> 本表默认值 0.80/0.50 为生产启动默认（application.yml），用户可按项目场景在「分析配置」中调整。

### 7.2 执行分析

点击「开始分析」，创建任务并进入执行。分析阶段：

```
初始化 → 需求解析(15%) → 形式化规约(35%) → 代码解析(50%)
      → 基础缺陷检测 → 一致性检查(70%) → 缺陷生成(85%) → 完成(100%)
```

- 进度条与执行日志**实时刷新**（WebSocket 推送）。
- 系统最多**并行执行 3 个分析任务**，超出排队等待。
- **重新分析**会复用上次权重/阈值配置；每次执行前自动清理旧的一致性/缺陷结果，不会叠加。

### 7.3 任务控制

| 操作 | 说明 |
|---|---|
| 暂停 | 任务进入「已暂停」，可随时恢复 |
| 恢复 | 从暂停点继续执行 |
| 终止 | 彻底停止任务，状态置「已终止」 |
| 重新分析 | 复用原任务配置发起新一轮完整分析 |

### 7.4 断点续跑（服务重启后）

若分析执行期间后端服务重启（或意外宕机）：

1. 任务状态自动变为「**已中断**」（红色标签），并给出中断原因提示。
2. 任务列表与任务卡出现「**续跑分析**」按钮。
3. 点击续跑后，**已完成的阶段自动跳过**（需求解析 / 规约生成 / 代码解析结果已入库的直接复用），从中断点附近继续，无需从零重跑。

> 任务历史记录了每次执行的完整日志，可点击「查看」回溯。

### 7.5 增量解析（改少量代码后重复分析，P2-5）

重新上传代码工程（或调整少量 `.java` 文件）后再次发起分析时，系统**默认启用增量解析**：

- 解析前按文件内容哈希（sha256）比对「存量解析结果」与「当前代码文件」，**未变更文件的方法单元整体复用**（跳过 AST 解析、语义向量化、LLM/结构化逻辑描述等重算），**只重解析变更/新增文件**，并自动清理已删除文件的历史单元；
- 执行日志会出现形如「增量比对：全部 N 个方法单元内容未变更，跳过代码解析」或「增量解析：变更/新增文件 x 个，移除 y 个…」的记录，用于核验命中情况；
- 老数据（升级前已解析、无内容哈希）首次分析会自动**全量重解析**一次并补齐哈希，之后即可增量；
- 若需关闭增量以强制全量，可在 `application.yml` 设置 `traceguard.analysis.incremental-code: false`（默认 true）。

## 8. 分析结果查看

分析完成后，从项目详情页或工作台进入结果体系：

### 8.1 需求条目（Requirements）

查看解析出的每条需求：编号、标题、描述、优先级、原始文档来源。

### 8.2 形式化规约

每条需求对应生成的形式化规约（前置条件/后置条件/不变式），含 Alloy 规约校验结果（合法/存疑及原因）。规约支持人工修订后参与后续一致性计算。

「查看规约」弹窗（需求列表 → 查看规约）额外提供**反例 / Kripke 状态迁移图**可视化（6.2 整改）：
- **Alloy 反例**：当规约求解产生反例（`counterexample`）时以红色等宽块展示反例文本；无反例时明确提示"未发现反例"。
- **Kripke 状态迁移图**：基于需求 Kripke 结构（`stateSet` / `stateTransitions`）渲染状态迁移图——初始状态绿色、转移边带条件标签、自环虚线，可拖拽/缩放；无状态数据时提示"无 Kripke 状态数据"。

### 8.3 代码单元（CodeView）

方法级代码单元清单：类名、方法签名、起始行号、圈复杂度、控制流图。

### 8.4 一致性矩阵（Results）

需求 × 代码单元的一致性得分矩阵：

- **完全一致**（绿）：得分 > T1
- **一般不一致**（黄）：T2 ≤ 得分 ≤ T1
- **严重不一致**（红）：得分 < T2

点击单元格查看分数构成（语义相似度/约束匹配度/不变量满足度三项明细）。

### 8.5 缺陷管理（Defects）

一致性缺陷 + 代码静态缺陷清单。列表含「**规则命中**」列——规则链路命中任一缺陷信号（数值不匹配/参数校验缺失/逻辑反转等）时显示综合风险徽标，未命中显示 `-`。

点击「详情」打开**分栏对比弹窗**：

- 左侧：需求原文；右侧：对应代码片段（**带真实起始行号**）
- 缺陷行号由 **AST 定位**（按缺陷子类型映射定位策略：约束缺失→方法体校验插入位、状态类→状态赋值行、数值类→冲突字面量比较行），无法解析时降级关键词启发式/方法首行
- 弹窗底部「**规则信号分解**」面板：逐条展示该缺陷命中的规则信号（中文名 + 贡献值 0~1，按贡献降序），综合风险标签标红/橙——规则判定结论的可解释性出口（数据来自缺陷的 `risk_signals` 字段）
- 支持缺陷状态流转（待处理/处理中/已解决/已忽略）

### 8.6 追溯矩阵（Traceability）

- **正向追溯**：需求 → 代码单元映射（covered / partially / uncovered）
- **反向追溯**：代码单元 → 需求关联（识别「多余实现」extra 代码）
- 支持中英文混合需求与代码命名的跨语言匹配。

### 8.7 多项目对比（FR-PLAT-003）

两个入口提供跨项目横向对比，均支持选择 **2~6 个**已完成分析的项目：

- **工作台（Dashboard）「多项目对比」卡片**：按覆盖率 / 质量评分 / 缺陷数对比，支持导出「多项目对比统计」Excel。
- **报告中心（ReportsHub）「跨项目对比档案」**：左侧勾选项目，右侧生成对比统计表与覆盖率对比图。

#### 8.7.1 质量洞察（W5 跨项目模块）

左侧菜单新增跨项目质量洞察模块，用于多项目横向治理：

- **缺陷趋势（DefectTrends）**：按时间窗（7/30/90 天）与项目维度查看跨项目缺陷趋势。
- **项目组合简报（PortfolioBrief）**：以报刊版式汇总在管项目组合质量简报（平均覆盖率与统计指标）。
- **缺陷工单（DefectTickets）**：跨项目缺陷治理台，按项目/等级/关键词过滤，支持状态流转闭环与误报就地标记。
- **缺陷模式（DefectPatterns）**：内置代码检测规则 × 真实命中数据的模式图鉴，可查看最近命中样例。
- **报告中心（ReportsHub）**：项目档案柜式报告管理，按项目取用各类分析报告，含跨项目对比档案。

#### 8.7.2 二期实验室（W6）

- **阈值实验室（ThresholdLab）**：可视化调参台，实时预览 `Sim = α·Cos + β·Con + γ·Inv` 公式与 T1/T2 分级效果；底部「规则信号权重」滑块可调 10 个缺陷规则信号（状态不匹配/数值不匹配/参数校验缺失/逻辑反转等）的权重（0=剔除噪声信号），点「保存权重」后经系统配置 `risk_weights` 热生效，下次分析按新权重合成缺陷风险分（管理员可见可写，默认值为网格实证基线：剔除 stateMismatch/impliedBusinessRuleMissing、numericMismatch×2、quantitativeBoundMismatch×1.5）。
- **评测中心（EvalCenter）**：展示内置标注资产（评测数据集）与阈值敏感性档案，支撑量化评测可追溯。
- **Alloy 工作台（AlloyLab）**：规约列表 / 代码编辑器 / 元数据与校验三栏式工作台，按项目加载 Alloy 规约并在线试算校验。

#### 8.7.3 系统运行状态（SystemStatus，仅管理员）

「系统设置 → 系统状态」页：概览数据库、磁盘、分析队列与实时连接的健康状态，支持手动刷新。

### 8.8 质量趋势与覆盖率图（Dashboard）

工作台（仪表盘）在概览卡片基础上新增：

- **质量趋势图**：按时间展示项目一致性率、缺陷密度的变化趋势，便于跟踪整改效果。
- **覆盖率环形图**：直观展示需求被代码覆盖的比例（covered / partially / uncovered）。

### 8.9 语义向量导出（FR-CODE-003）

- 在「代码管理」与「一致性分析（结果）」页均提供「**导出语义向量**」按钮，按项目导出需求与代码单元的语义向量。
- 支持 **JSON** 与 **CSV** 两种格式（代码管理页可选格式，结果页默认 JSON），用于离线分析或二次建模。

### 8.10 追溯矩阵独立 PDF 导出（4.3 整改）

「追溯矩阵」页提供「**导出矩阵 PDF**」按钮，一键将需求-代码追踪关系矩阵单独导出为排版规整的 PDF（与综合分析报告 PDF 解耦，便于单独分发审阅）。

### 8.11 形式化规约优化建议展示（2.6 整改）

## 13.5 大模型（LLM）能力配置（可选，默认关闭）

本系统的大模型能力属于**可选增强**，**默认处于关闭状态**（GAP-033、AUD-04）。在不配置任何大模型 API 的情况下，系统基于规则即可完成全部核心功能（需求解析、形式化建模、一致性校验、缺陷检测），无需外部网络或密钥。

- **何时需要开启**：仅当你希望使用「缺陷智能解释」「修复建议」等由大模型提供的增强能力时。
- **如何开启（管理员）**：
  1. 进入「系统设置 → LLM 配置」；
  2. 打开「启用大模型」，选择 provider（如 `deepseek` / `openai` / `qwen`），填写 `baseUrl` 与 `apiKey`；
  3. 点击「保存」并「测试连通性」，状态变为「已启用」即生效。
- **未配置时的表现**：`/llm/status` 返回 `enabled=false`，相关增强按钮自动降级或隐藏，主流程不受影响。
- **演示配置**：仓库根目录提供 `.env.example` 模板（变量 `LLM_ENABLED` / `LLM_PROVIDER` / `LLM_BASE_URL` / `LLM_API_KEY`），复制为 `.env` 并填入真实 `apiKey` 即可；该模板不含任何真实密钥。
- **安全提示**：`apiKey` 仅存储于服务端配置，前端接口均做脱敏处理，请勿将真实密钥提交至版本库。

### 13.5.1 自然语言向量化（Embedding，可选增强，需显式开启）

需求/代码语义向量化（GAP-004）同样属于**可选增强能力**，请勿视为默认生产路径：
- **默认 provider=local（BGE 离线 ONNX）**：`traceguard.llm.embedding.provider=local` 时使用本地 BGE 模型离线向量化，零外部依赖；但**需先下载模型**（`scripts/download_bge_model.sh`，约数百 MB）并配置 `EMBEDDING_MODEL_PATH`（指向 `model.onnx`，与 `vocab.txt` 同目录）。
- **模型缺失 / 未配置时**：`EmbeddingService.available()` 返回 `false`，系统**自动降级为规则匹配路径**（基于词典/相似度），主流程不受影响，仅损失跨语言语义表征精度。
- **可选云端**：`EMBEDDING_PROVIDER=openai` 并配置 `EMBEDDING_API_KEY` 可切换云端文本向量化。
- **一句话**：向量化需显式配置（本地模型或云端 Key）后才启用；未配置时系统以规则模式照常运行，不会报错。

## 13.6 本地 CodeLlama + LangChain 真集成（GAP-043 / GAP-044）

除云端模型外，系统**原生存支持本地开源 CodeLlama 推理**与 **LangChain（langchain4j）编排**，无需任何云端 API Key，满足申报书「基于开源 CodeLlama + LangChain 框架研发自动转换引擎」的承诺。Ollama 提供 OpenAI 兼容的 `/chat/completions` 端点，后端 `OpenAiLlmClient` 直接复用，CodeLlama 即走本地真实推理。

### 13.6.1 安装并拉起 Ollama（本地模型服务）

1. 下载安装 Ollama：https://ollama.com
   - **Windows 自定义路径（推荐避免占用 C 盘）**：图形安装向导不显示路径选择，用命令行指定：
     ```powershell
     # 指定程序安装目录（先关闭已打开的安装窗口）
     Start-Process "OllamaSetup.exe" -ArgumentList '/DIR="D:\develop\Ollama"' -Wait
     # 指定模型存放目录（约 3.8GB/7b）
     [Environment]::SetEnvironmentVariable("OLLAMA_MODELS", "D:\develop\Ollama\models", "User")
     ```
     安装器会自动把 `D:\develop\Ollama` 加入用户 PATH，重开终端即可直接用 `ollama` 命令。
2. 拉取并启动 CodeLlama：
   ```powershell
   ollama pull codellama:7b            # 显存不足可选 codellama:7b-instruct 或 13b
   # Ollama 安装后默认后台自启并监听 11434；可用以下命令验证：
   curl http://localhost:11434/api/tags
   ```
   仓库同时提供一键脚本 `scripts/pull-codellama.sh`（Git Bash / WSL：`bash scripts/pull-codellama.sh`）。

### 13.6.2 启用 CodeLlama（无需改配置）

`application.yml` 的 `traceguard.llm.providers` 已内置 `codellama`（base-url 默认 `http://localhost:11434/v1`，可用 `CODELLAMA_BASE_URL` 覆盖）。只需把一致性判定路由指向它即可：

```yaml
traceguard:
  llm:
    enabled: true
    providers:
      codellama:
        base-url: ${CODELLAMA_BASE_URL:http://localhost:11434/v1}
        api-key: ""        # Ollama 不校验密钥，留空即可
    engine: ${LLM_ENGINE:self}      # self=OpenAI 兼容客户端；langchain=langchain4j 编排
    routing:
      consistency-check: codellama
    models:
      consistency-check: codellama:7b
```

> 本地模型 `api-key` 为空也能启用——base-url 指向本机（localhost/127.0.0.1）时视为可用。

### 13.6.3 切换引擎（self / langChain）

- **`engine: self`（默认）**：直接用 `OpenAiLlmClient` 调用本地 CodeLlama，零额外依赖。
- **`engine: langchain`**：**LangChain 真集成**——`LangChainAdapter` 以 langchain4j 的 `OpenAiChatModel` 编排「需求-代码一致性判定」链。langchain4j 为 `optional` 依赖，缺失或下游异常时 `ConsistencyJudge` **自动回退 self 引擎**，主流程不中断。

生产环境通过环境变量切换（无需改 yml）：

```powershell
$env:LLM_ENGINE="langchain"        # 启用 LangChain 编排（GAP-044）
$env:CODELLAMA_BASE_URL="http://localhost:11434/v1"
$env:CODELLAMA_MODEL="codellama:7b"
```

### 13.6.4 连通性测试

- 管理端「系统设置 → LLM 配置 → 测试连通性」选择 `codellama` provider；
- 或调用后端接口 `POST /api/llm/test?provider=codellama`，返回模型回复即打通。

### 13.6.5 评测演示（端到端真集成）

```powershell
cd D:\Develop\TraceGuard\backend
# LangChain 编排本地 CodeLlama
$env:LLM_PROVIDER="codellama"; $env:LLM_ENGINE="langchain"
mvn -B test -Dtest=DefectDetectionEvalTest
# 仅 self 引擎（OpenAI 兼容客户端直连 CodeLlama）
$env:LLM_PROVIDER="codellama"; $env:LLM_ENGINE="self"
mvn -B test -Dtest=DefectDetectionEvalTest
```

> 本仓库 CI 环境无本地 GPU/Ollama，真集成代码已落地并通过编译与默认引擎回归；**端到端 CodeLlama×LangChain 推理需在本机按上述步骤拉起 Ollama 后复测**。若 Ollama 未启动或路径错误，`engine=langchain` 会自动回退 `self`，日志出现 `GAP-044：... 回退 self 引擎` 提示，主流程不中断。
>
> **实测结论（2026-08-27）**：CodeLlama:7b 指令遵循不足，JSON 判定成功率 <10% 无法达标；实际评测采用 `qwen2.5-coder:14b`（`CODELLAMA_MODEL=qwen2.5-coder:14b`）+ FUN-04b 双判定管线——LLM 判定成功 55/55=100%，缺陷检测准确率 **96.4%**、漏检率 **3.8%**、误报率 **3.4%**，SRS 三项指标全部达标（详见 `docs/03-报告/评测报告-综合.md`）。

## 13.7 集成连通测试（仅管理员，AUD-11）

系统提供与第三方工具对接的标准化 REST 接口：**Jira / 禅道**（项目管理工具，需求导出为 Issue、缺陷推送）与**企业微信 / 钉钉**（Webhook 群机器人通知）。**连通测试**用于确认配置是否正确、网络是否可达：

- **配置来源**：后端按环境变量读取——Jira（`JIRA_BASE_URL` / `JIRA_USER` / `JIRA_TOKEN` / `JIRA_PROJECT_KEY`）、禅道（`ZENTAO_BASE_URL` / `ZENTAO_TOKEN` / `ZENTAO_PRODUCT_ID`）、企业微信（`WECOM_BASE_URL` / `WECOM_KEY` / `WECOM_SECRET`）、钉钉（`DINGTALK_BASE_URL` / `DINGTALK_TOKEN` / `DINGTALK_SECRET`）。默认 `enabled=true` 但指向演示占位端点，生产须覆盖为真实服务地址与凭据。
- **入口**：管理员进入「系统设置 → 集成连通测试」（Jira/禅道/企业微信/钉钉四卡片）；或在「需求」页「导出为 Issue」按钮旁、「缺陷」页「推送」按钮旁点击「测试连通」快捷按钮。
- **结果展示**：页面加载时后端通过 `/api/integration/status` 返回各工具**配置摘要**（服务地址、项目标识/产品 ID/机器人 Key/AccessToken、凭据是否已配置，凭据原文不返回、界面仅标记「已配置/未配置」），卡片直接展示实际生效值而非占位符；点击「测试连通」后展示成功（含版本信息）或失败原因（未配置时明确提示「集成未启用」，便于区分配置问题与网络问题）。企微/钉钉的「测试连通」会实际向群机器人发送一条测试消息。
- **连通成功后的用途**：
  - **Jira / 禅道**：连通测试是需求导出/缺陷推送的前置安全门——只有可达且认证通过才允许调用 `POST /api/integration/requirements/export`（需求导出为 Jira Story/禅道需求）与 `POST /api/integration/defects/push`（缺陷推送为 Bug）。推送幂等：已推送记录（`remote_issue_key` 非空）自动走 update，不重复创建，成功后回写 `remote_issue_key`。
  - **缺陷状态回写（出站联动）**：本地缺陷状态流转（处理中/已解决/不予解决）时，若该缺陷已推送过（`remote_issue_key` 非空）会自动同步远程 issue 状态，失败不影响本地流转。
  - **需求变更联动（出站）**：需求列表操作列对已导出需求（显示远程 Issue Key 徽标）提供「同步到远程」按钮——本地需求内容变更后，一键调用 `PUT /api/integration/requirements/sync/{requirementId}` 把最新标题/描述幂等更新到远程 issue。
  - **入站自动同步（远程→本地，轮询）**：无需公网地址。**默认开启**（`INBOUND_SYNC_ENABLED` 默认 `true`），后端每 `cron` 周期（默认 5 分钟）自动拉取所有已推送缺陷（`remote_issue_key` 非空）在 Jira/禅道的状态变化，映射为本地统一状态并回写（走合法状态流转 + 审计日志）；可用 `INBOUND_SYNC_ENABLED=false` 关闭、`INBOUND_SYNC_CRON` 调整频率。可在「集成连通测试」页调用「立即同步」按钮（`POST /api/integration/sync/inbound`）手动触发，或查看「同步状态」（`GET /api/integration/sync/inbound/status`）了解最近一次扫描数/变更数/耗时。演示环境可把 `INBOUND_SYNC_CRON` 设为 `*/20 * * * * *` 每 20 秒观察效果；配合 `integration-mock` 调试端点 `POST http://localhost:18084/__simulate`（`{"platform":"jira","key":"ISSUE-101","status":"Done"}`）可模拟远程状态变化触发本地回写。
  - **企业微信 / 钉钉**：点击「发送测试通知」通过 `POST /api/integration/notify` 向群机器人发送 markdown 通知（消息支持标题/正文/详情链接）；支持机器人加签（HMAC-SHA256），消息发送失败自动熔断降级，不阻断主流程。

## 13.8 Windows 一键部署（可选，AUD-12）

除 Docker 部署外，Windows 10/11 原生环境可通过脚本一键部署（两种方式并存）：

1. **前置安装**（均加入系统 Path）：JDK 21+、Maven 3.8+、MySQL 8.0+、Node.js 20 LTS+。
2. 在项目根目录 PowerShell 执行：
   ```powershell
   powershell -ExecutionPolicy Bypass -File scripts\deploy-windows.ps1 -MysqlUser root -MysqlPass '你的密码'
   ```

4. 常见问题：端口占用（改 `application-prod.yml` / `vite.config.js`）、数据库连接失败（检查 MySQL 服务与密码）、生产密钥加固（设置 `JWT_SECRET` 等环境变量后再启动）。

## 14. 常见问题（FAQ）

**Q1：上传需求文档后解析出 0 条需求？**
检查文档是否为受支持的格式、内容是否含可识别的需求编号（建议使用 `REQ-001:` 风格编号开头）。

**Q2：上传代码 ZIP 提示"未找到 Java 源文件"？**
请确认压缩包内直接包含 `.java` 源码（常见错误：把整个工程连同 build 产物一起打包，或只打了空目录）。建议打包 `src` 目录。

**Q3：任务显示"已中断"？**
后端服务重启导致，属正常保护机制。点击「续跑分析」即可，已完成阶段自动跳过。

**Q4：大文件上传失败后重新选择文件，会重复占用空间吗？**
分片会话在合并完成或失败清理后释放临时目录；重传时自动跳过已传分片，不会重复存储。

**Q5：忘记备份口令怎么办？**
备份口令不可找回。若已忘记，只能重新设置口令并创建新备份（旧备份文件将无法解密恢复）。

**Q6：重新分析后缺陷列表出现重复？**
不会。每次分析执行前系统自动清理旧的一致性与缺陷结果。

**Q7：一致性得分总是偏低？**
优先检查：① 需求描述是否过于简略（关键词过少）；② 代码方法命名是否与需求术语一致；③ 可在「分析配置」中调低 T1/T2 阈值或调整 α/β/γ 权重后重新分析对比。

**Q8：登录时提示"账号已临时锁定"？**
同一账号连续登录失败 5 次触发保护机制，锁定 10 分钟后自动解锁，期间请勿反复尝试。
